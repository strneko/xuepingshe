# 社区点赞与评论通知技术报告

## 1. 背景

社区模块已经具备帖子、评论、点赞、SSE 通知中心和消息列表等基础能力。此次实现的目标是把“有人点赞或评论帖子，贴主收到通知”接入现有通知架构，而不是再新增一套独立通知系统。

## 2. 结论

当前项目的通知架构适合承载社区点赞与评论通知。原因有三点：

1. 已有统一的通知入队能力，支持批量收件人、去重和消息持久化。
2. 已有用户消息列表、未读数、已读/删除接口，以及 SSE 实时推送。
3. 社区点赞与评论本身是标准的“业务事件”，适合在业务写库成功后作为后处理写入通知中心。

## 3. 实现原则

实现时遵循了以下原则：

1. 业务主流程优先。
   点赞、评论成功是第一目标，通知失败不应反向影响主流程。
2. 通知逻辑集中封装。
   点赞/评论 route 只负责业务写库，通知拼装统一放到社区专用辅助模块。
3. 去重可控。
   使用通知中心已有的 dedupeKey 机制，避免重复提交、重试或并发导致的刷屏。
4. 避免自通知。
   贴主自己给自己的帖子点赞/评论时，不创建通知。

## 4. 架构设计

新增了一个社区专用通知辅助模块：

- [lib/community/notifications.ts](../lib/community/notifications.ts)

该模块负责：

1. 过滤收件人，自动排除当前操作者本人。
2. 组装点赞/评论通知的标题、摘要、跳转链接和 payload。
3. 生成稳定的 dedupeKey，交给统一通知中心入队。

社区接口的职责保持单一：

- [app/api/community/posts/[postId]/like/route.ts](../app/api/community/posts/[postId]/like/route.ts)
- [app/api/community/posts/[postId]/comments/route.ts](../app/api/community/posts/[postId]/comments/route.ts)

这两个接口仍然只负责：

1. 校验输入。
2. 写入点赞/评论。
3. 更新帖子统计字段。
4. 在事务提交后触发通知入队。

## 5. 数据流

### 5.1 点赞通知

1. 用户发起点赞请求。
2. 服务端在事务内检查帖子是否存在、当前用户是否已点赞。
3. 只有“点赞成功”时才准备通知上下文。
4. 事务提交后，将通知写入通知中心。
5. 贴主通过通知列表与 SSE 实时收到消息。

点赞通知的收件人只包含贴主本人；如果操作者就是贴主，则收件人集合为空，通知直接跳过。

### 5.2 评论通知

1. 用户发表新评论。
2. 服务端在事务内写入评论并更新评论数、最后回复时间和热度。
3. 如果是回复评论，则先校验被回复评论是否存在。
4. 事务提交后，通知会发给：
   - 帖子作者
   - 被回复评论作者（如有且不等于操作者本人）
5. 通知中心统一去重、入库并推送。

## 6. 容错策略

通知属于次级能力，因此采用“失败不阻断主流程”的策略：

1. 点赞/评论写库成功后，即使通知入队失败，主操作仍然返回成功。
2. 通知失败会记录到服务端日志，便于后续排查。
3. 通知中心自身使用 dedupeKey，避免请求重试造成重复通知。

## 7. 去重策略

通知中心已有统一 dedupeKey 能力。此次实现中使用了稳定的业务键：

1. 点赞通知：基于事件类型、帖子 ID 和收件人集合生成。
2. 评论通知：基于事件类型、评论 ID 和收件人集合生成。

这样可以保证：

1. 同一业务事件的重复提交不会产生多条通知。
2. 不同收件人组合天然隔离。
3. 评论和点赞两类事件互不干扰。

## 8. 代码落点

本次实现主要涉及以下文件：

- [lib/community/notifications.ts](../lib/community/notifications.ts)
- [app/api/community/posts/[postId]/comments/route.ts](../app/api/community/posts/[postId]/comments/route.ts)
- [app/api/community/posts/[postId]/like/route.ts](../app/api/community/posts/[postId]/like/route.ts)

其中：

1. `lib/community/notifications.ts` 负责通知文案、收件人过滤和 dedupeKey。
2. 评论接口补充了回复评论校验、作者信息与通知入队。
3. 点赞接口只在实际点赞成功时创建通知。

## 9. 验证结果

已完成以下验证：

1. TypeScript 类型检查通过。
2. ESLint 定向检查通过。
3. 通知中心与社区接口的职责边界保持清晰，没有把通知逻辑散落到页面组件中。

## 10. 后续可扩展方向

如果后续继续增强，可以优先考虑：

1. 给通知 payload 增加更丰富的业务字段，方便后续做通知详情页跳转。
2. 增加“评论被回复”与“帖子被收藏”等更多社区事件。
3. 如果业务量继续增长，可以把通知入队进一步抽象成异步任务或消息队列。

## 11. 结语

当前实现采用的是“业务事件 + 统一通知中心”的方式，结构清晰、可扩展性较好，也符合现有项目中 SSE 通知体系的设计风格。对于社区点赞与评论通知，这套方案已经足够稳定，也便于后续继续扩展其他互动通知。
